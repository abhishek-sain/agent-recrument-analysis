# Frontend Integration Guide — Onboarding Link

This document explains how the frontend app should consume the onboarding
link generated by the backend, step by step, with example API calls.

## 1. What the backend sends you

When an SM generates a link, the backend returns something like this:

```json
{
  "id": "TKT-12-09-2026-143059-7",
  "token": "nO5Z-N3WFXRNlU2pPv3Zd57-SMegNOmiNxWvlUIq-Cc",
  "onboarding_url": "http://localhost:3000/onboard/pos/nO5Z-N3WFXRNlU2pPv3Zd57-SMegNOmiNxWvlUIq-Cc",
  "share": {
    "copy_link": "http://localhost:3000/onboard/pos/nO5Z-...",
    "whatsapp": "https://wa.me/9876543210?text=...",
    "sms": "sms:9876543210?body=..."
  }
}
```

The important part: `onboarding_url` already points at **your** frontend
route (`FRONTEND_BASE_URL` in the backend's `.env`) — the backend does not
render any page. It only builds this URL string and hands it to the SM to
share via WhatsApp/SMS/copy-link.

The `token` embedded in that URL is the only thing the frontend needs to
drive the entire onboarding flow. It is not a login/session token — it is
a single-use key that identifies **one onboarding record**.

`id` (e.g. `TKT-12-09-2026-143059-7`) is the record's primary key - a
human-readable ticket id (`<PREFIX>-dd-mm-yyyy-HHMMSS-<n>`), not a UUID.
Useful for display/reference (e.g. an ops dashboard), but the frontend
should keep using `token` to drive the flow, never `id`.

## 2. Route the frontend must implement

Create a route shaped like:

```
/onboard/:userType/:token
```

Examples:
- `/onboard/pos/nO5Z-N3WFXRNlU2pPv3Zd57...`
- `/onboard/pos-referral/O6wPq41xX1Jgd3Nk...`

`userType` is just a hint for which form variant to render (`pos` vs
`pos-referral`) — always trust the `user_type` field returned by the API
below as the source of truth, not the URL segment.

## 3. Step-by-step flow the page should follow

### Step 1 — Resolve the token (on page load)

```js
const res = await fetch(`${API_BASE_URL}/api/v1/links/${token}`);

if (res.status === 404) {
  // invalid/unknown token -> show "invalid link" screen
}
if (res.status === 200) {
  const data = await res.json();
  // render form based on data.user_type, prefill name/number
}
```

Response shape:
```json
{
  "id": "TKT-12-09-2026-143059-7",
  "name": "Ramesh Kumar",
  "number": "9876543210",
  "user_type": "POS",
  "status": "LINK_GENERATED"
}
```

### Step 2 — Fill the onboarding form

The form captures: `dob`, `email`, `city`, `state`, `pincode`, `consent`.
Save with:

```js
await fetch(`${API_BASE_URL}/api/v1/onboarding/${token}/form`, {
  method: "PUT",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    dob: "1990-01-15",
    email: "ramesh@example.com",
    city: "Pune",
    state: "Maharashtra",
    pincode: "411001",
    consent: "AGREE",
  }),
});
```

This endpoint can be called multiple times (e.g. save-as-you-go / a
"Next" button per section) — it upserts the record each time.

`terms_and_conditions` is **not** part of this payload. It's fixed at
creation to `"we can use your data for onboarding you"` and shown
read-only on the consent screen (the `GET` response includes it). It has
its own endpoint, kept separate on purpose so the legal text can be
corrected/updated later without touching anything else on the record:

```js
await fetch(`${API_BASE_URL}/api/v1/onboarding/${token}/terms-and-conditions`, {
  method: "PUT",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ terms_and_conditions: "updated text" }),
});
```

### Step 3 — Upload documents

One request per document, as multipart form-data:

```js
const form = new FormData();
form.append("file", fileInput.files[0]);

await fetch(
  `${API_BASE_URL}/api/v1/onboarding/${token}/documents?doc_type=PAN_CARD`,
  { method: "POST", body: form }
);
```

`doc_type` values: `PAN_CARD`, `AADHAAR`, `EDUCATIONAL_QUALIFICATION`,
`PHOTOGRAPH`, `CANCELLED_CHEQUE`.

The response gives back the stored file URL — you can use it to show a
preview/thumbnail on the review screen.

If you extract structured fields from these documents (OCR or manual
entry), save them with `PUT /api/v1/onboarding/{token}/documents/pan-details`,
`.../aadhaar-details`, `.../education-details` — these write into the
`document_details` table (Table-2), one row per record.

### Step 4 — Review & Submit

Show a read-only summary (call `GET /api/v1/onboarding/{token}` to fetch
the full current record), then:

```js
const res = await fetch(`${API_BASE_URL}/api/v1/onboarding/${token}/submit`, {
  method: "POST",
});

if (res.status === 422) {
  const { detail } = await res.json();
  // detail.missing -> list of missing required fields/documents, show inline errors
}
if (res.status === 409) {
  // duplicate mobile number already onboarded/in review
}
if (res.status === 200) {
  // show "Submitted for review" success screen
}
```

### Step 5 — If ops sends it back for corrections

Ops can send the record back with `SEND_BACK`. This **rotates the
token** — the old link stops working, and a new `onboarding_url` is
generated. The SM (or your notification system) resends that new link to
the POS/Referral the same way as step 1. There is nothing special the
frontend needs to code for this beyond re-running the same flow against
the new link.

## 4. Status values you may see from `GET /api/v1/links/{token}` or `GET /api/v1/onboarding/{token}`

| status | meaning | what the frontend should show |
|---|---|---|
| `LINK_GENERATED` | link created, form not yet started | form screen |
| `FORM_IN_PROGRESS` | form saved at least once | continue form / resume |
| `UNDER_REVIEW` | submitted, being reviewed by ops | "submitted, under review" read-only screen |
| `SEND_BACK` | old token invalidated | show "link expired, request a new one" (a new link/token will be issued) |
| `REJECTED` | rejected | "onboarding rejected" screen |
| `APPROVED` / `ACTIVE` | approved & activated | "onboarding complete" screen |

## 5. Things to configure on the frontend

- `API_BASE_URL` — environment variable pointing at the FastAPI backend
  (e.g. `http://localhost:8000` in dev).
- CORS: the backend's `.env` has `CORS_ORIGINS` — make sure your
  frontend's dev/prod URLs are added there, otherwise browser requests
  will be blocked.
- No auth headers are needed for any of the onboarding-flow endpoints
  above — the `token` in the URL is the only credential. Admin/ops
  endpoints (`/api/v1/admin/...`) should be called only from screens
  protected by your existing login system.
